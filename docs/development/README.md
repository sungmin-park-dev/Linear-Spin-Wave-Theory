# 2D Spin-System Toolkit — 개발 목표와 시스템 설계

개발 목표, 시스템의 계산 흐름, 모델 공통 전달 규약과 모듈별 책임을 설명하는
Beamer PDF다. 구현·검증 기록은 설계를 뒷받침하는 부록으로 관리한다.
현재 검토본은 11이며, 기록일은 2026-09-29이다.

## 로컬에서 검토하기

기본 저장소의 `docs/development/`에서 편집·검토한다. `main.tex`가 진입점이며,
본문은 `sections/`, 구현·검증 근거는 `appendices/`에 있다. PDF는
`output/pdf/development-log.pdf`를 연다. `make qa`는 중간 파일을 `build/`에만
모으고 PDF를 `output/pdf/`에 갱신한다.

2026-09-23 작업 사본의 코드·문서를 기본 저장소에 통합했다.
[통합 검증 기록](verification/local-integration-2026-09-23.json)은
기존 로컬 변경 보존, 테스트, 수치 대조와 PDF 빌드 확인을 기록한다.

## 문서 구성

1. **개요**: 문서의 역할·구성, 도구의 개발 목표와 1차 개발 범위
2. **시스템 구조와 계산 흐름**: 모델 정의부터 계산·물리량 분석·시각화·저장까지의 블록 구조, 구성요소별 책임, 외부 변수 분류, 상태와 계산계의 정합 조건
3. **공통 자료구조와 전달 규약**: 모델·사이트·항(`terms`)의 의미, 해밀토니안과 장의 규약, Fourier 부호와 위치 게이지, 검증, 세부 규칙 결정, 상태·계산 요청·결과
4. **모듈과 폴더 구성**: 목표 패키지 `spintoolkit`, 표준 벤치마크 모델 위치, 모델별 계산과 결과 보관 위치
5. **개발 계획**: 구현 단계 0–5, 벤치마크 검증 기준, 후속 키타에프 벤치마크

- **부록 A. 구현·검증 기록**: 구현 현황, 수치 대조, 이행 문제와 확인 조건, 미결 사항
- **부록 B. 결정·관리·참고자료**: 결정 사항, 문서 갱신 방식과 근거

이 구성은 개발 과정에서 조정할 수 있다. 본문에는 설계의 의미와 방향을 두고,
세부 구현 이력과 시험 수치는 부록에서 참조한다.

## 파일과 상태

- `main.tex`: 제목·공통 설정·목차와 섹션 입력 순서를 관리하는 진입 파일.
- `sections/`: 본문의 다섯 섹션. 목적과 기능 단위로 나누어 편집한다.
- `appendices/`: 구현·검증 기록과 결정·관리·참고자료.
- `knowledge-factory-beamer.sty`: Knowledge Factory에서 가져온 수정하지 않은 theme 사본.
- `source-manifest.json`: theme 출처·버전·해시와 이 기록에 사용한 프로젝트 소스의 해시.
- `output/pdf/development-log.pdf`: 생성되는 PDF.
- `output/qa.json`: 기계적 문서 검수 결과. 전 페이지 시각 검수는 별도로 기록한다.
- `output/visual-review.json`: 검토한 PDF 해시와 페이지별 시각 검수 범위를 기록한다.
- `verification/package-layout-2026-09-23.json`: 기능별 폴더 이행의 소스·수치·호환성 검증 기록.
- `build/`: 빌드 중간 파일. 생성 PDF와 함께 기본 Git 추적에서 제외한다.

검토본 01은 이전 NBCP 추출 기록을 대조했다. 검토본 02에서는 기능별 폴더 이행
전후의 테스트와 수치 대조를 새로 수행했다. 기존 추출 기록과 새 이행 기록을
별도 근거로 유지한다.
검토본 03은 문서 목적과 섹션 구성을 정리한 개정이며, 수치 검증을 새로 실행하거나
기존 검증의 범위를 확대하지 않는다.
검토본 04에서는 문서가 설명할 내용과 도구가 제공할 기능·초기 지원 범위를
구분했다. 사용자가 확정한 문서 목적은 유지한다.
검토본 05에서는 시스템 구조를 전체 계산 흐름과 구성요소별 책임의 두 슬라이드로
정리했다. 현재 구현 기반과 향후 확장을 구분하며, 코드와 상세 API 규약은 변경하지 않는다.
검토본 06에서는 전체 도식을 입력 준비와 계산·결과 활용의 두 장으로 나누고,
구성요소별 책임 표를 그다음 장에 배치했다. 블록의 글자와 간격을 늘려 가독성을 개선했다.
검토본 07에서는 계산격자 조건을 계산계 구성 바로 아래에 배치하고, 모호했던
‘후보 스핀상태’를 ‘스핀 배열’로 바꾸어 고전 최적화의 초기 배열·LSWT 기준 배열이라는 의미를 설명했다.
검토본 08에서는 ‘계산 대상 스핀계’를 모델과 계산격자 조건의 결합으로 정의하고,
스핀 배열이 전달하는 정보는 ‘스핀 방향·자기구조의 반복주기’로 명확히 했다.
검토본 09에서는 2026-09-29 사용자와 확정한 1차 개발 범위와 규약 결정을 반영했다.
반영한 결정은 다음과 같다: 해밀토니안으로서의 모델, 외부 변수 분류, 상태와 계산계의 정합,
`terms[]` 형식, g-텐서와 외부 장 `B`, `-mu_B` 부호, 두 하이젠버그 벤치마크와 최소 ED 검증 도구,
`spintoolkit` 패키지, 키타에프 후속 벤치마크.
상세 규약 문서를 먼저 갱신하고 이 문서의 요약을 맞췄다. 사용자가 결정하지 않은
세부 규칙은 슬라이드에 ‘[제안]’으로 표시하고 검토 요청 쪽에 모았다.
코드와 수치 검증은 변경하지 않았다.
검토본 10에서는 세부 제안 네 가지에 대한 사용자 결정을 반영했다. `zeeman` 항은
선택 사항으로 바꿨고, `g_(alpha beta)` 인덱스와 relative 단위의 `mu_B = 1`은 확정했다.
또 상태 검증과 기준 상태 진단(정상성·안정성)을 나눴다. 검토 요청 쪽은 결정 기록 쪽으로
바꾸고, 결정 기록에 D12를 추가했다.
검토본 11에서는 미결 사항에 대한 사용자 결정을 반영했다. 고체물리 표준 Fourier 부호와
전체 위치 게이지를 툴킷 규약으로 채택했고, 이에 따라 NBCP 결합 변위를
`r_target = r_source - d`로 해석하고 변환 규칙을 정했다. 이 해석은 2단계에서 수치로 확정한다.
상태·계산 요청·결과는 공통 부분과 방법별 부분으로 나눠 `SpinState`, 공통 요청,
결과 머리부와 LSWT 본문의 검토안을 추가했다. 표준 벤치마크 모델은 `spintoolkit/models/`에 둔다.
결정 기록은 두 쪽으로 나누고 D13–D15를 추가했다.

## 템플릿 출처

Knowledge Factory의 `templates/knowledge-factory-beamer/`를 사용했다.
선언 버전은 v0.2.3이며, 원본 저장소 HEAD와 실제 `.sty` 파일 해시를 manifest에
기록했다. 가져온 파일은 당시 **미커밋 변경이 있는 로컬 스냅샷**이다.
따라서 해당 HEAD의 정식 배포 파일과 동일하다고 주장하지 않는다.
원본 저장소와 theme 사본은 수정하지 않고 문서에서만 표준 Beamer 설정을 적용했다.
도식은 이 설계 문서를 위해 직접 작성했다.

## 빌드와 검수

XeLaTeX, latexmk, Poppler의 `pdfinfo`, `pdffonts`, `pdftotext`, Python 3가 필요하다.

```sh
cd docs/development
make qa
pdftoppm -scale-to 1600 -png output/pdf/development-log.pdf /tmp/lswt-development-page
```

`make qa`는 PDF를 빌드한 뒤 로그, 페이지 수, 글꼴 임베딩, frame label,
본문·부록 배치, theme·근거 소스의 해시, 본문 추출을 검사한다.
편집 원본은 모든 섹션 입력을 포함해 해시로 기록한다. 전 페이지의 표·도식·글자 겹침은
렌더링한 이미지로 확인한다. 빌드 성공과 내용의 물리적 타당성은 별도 상태다.

## 갱신 방식

1. 규약을 변경하면 상세 Markdown을 먼저 갱신하고 이 문서의 요약을 맞춘다.
2. 개발 목표·구조·규약·계획은 `sections/`의 해당 섹션을 갱신한다.
3. 구현이 바뀌면 관련 검증을 다시 수행하고 조건·결과·실패 목록을 부록에 연결한다.
   결정 사항은 `appendices/`, 문서 제목·기록일·섹션 순서는 `main.tex`에서 관리한다.
4. 근거를 검토한 뒤 `source-manifest.json`의 해당 해시를 갱신한다.
   검수 오류를 없애기 위해 근거 검토 없이 일괄 갱신하지 않는다.
5. `make qa`와 전 페이지 시각 검수를 마친 PDF를 확인한다.

미래 ED/TN 구현, 캐시, 빈 모델 폴더는 이번 문서 작업으로 생성하지 않았다.
